## How does running time grow?

A program that's instant on 100 samples can take hours on 10 million. **Algorithmic complexity** describes how the work grows with the input size $n$, ignoring constant factors, using **big-O** notation:

| Complexity | Name | $n = 10^6$: rough operations | Example |
|---|---|---|---|
| $O(1)$ | constant | 1 | array indexing, hash-table lookup |
| $O(\log n)$ | logarithmic | 20 | binary search |
| $O(n)$ | linear | $10^6$ | scanning an array, a moving average |
| $O(n\log n)$ | linearithmic | $2\times10^7$ | good sorting, the FFT |
| $O(n^2)$ | quadratic | $10^{12}$ | naive sorting, naive DFT, comparing all pairs |
| $O(2^n)$ | exponential | impossible | brute-force search over subsets |

At $10^9$ simple operations per second, the $O(n^2)$ row takes 17 minutes where $O(n\log n)$ takes 20 ms. Choosing the right algorithm matters far more than micro-optimizing code. The FFT (DSP, Lesson 2.2), which turned an $O(n^2)$ computation into $O(n\log n)$, is the classic example.

## Searching

- **Linear search** checks each element: $O(n)$.
- **Binary search** on **sorted** data halves the range each step: $O(\log n)$.

```python
def binary_search(a, target):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == target:  return mid
        if a[mid] < target:   lo = mid + 1
        else:                 hi = mid - 1
    return -1
```

Finding a value among $10^6$ sorted entries takes at most 20 comparisons. The same idea finds a threshold crossing in sorted measurements, a register value in a lookup table, or the bug-introducing commit with `git bisect` (next lesson). The successive-approximation ADC (Embedded Systems, Lesson 2.4) is a binary search in hardware.

## Sorting

- **Insertion sort** builds a sorted prefix one element at a time: $O(n^2)$ in general, but fast for tiny or nearly sorted arrays.
- **Merge sort** splits the array in half, sorts each half recursively, then merges: $O(n\log n)$ always.
- **Quicksort** partitions around a pivot: $O(n\log n)$ on average, the usual library choice (with safeguards).

In practice, call the library (`sorted()` / `np.sort` in Python, `qsort` in C): they're well tested and fast. Know the complexity so you can predict how your program scales.

## Data structures matter too

| Operation | Python list (array) | Dict / set (hash table) |
|---|---|---|
| index by position | $O(1)$ | — |
| find a value | $O(n)$ | $O(1)$ average |
| insert at end | $O(1)$ amortized | $O(1)$ average |
| insert at front | $O(n)$ | — |

Checking membership in a list inside a loop gives an accidental $O(n^2)$ program; converting the list to a set first makes it $O(n)$. In embedded systems, **ring (circular) buffers** give $O(1)$ queues with fixed memory, the standard way to pass data from interrupts to the main loop.

## Measuring

Complexity predicts scaling; **profiling** finds where time actually goes. Measure before optimizing (Python's `timeit` and `cProfile`, or toggling a GPIO pin around a routine and watching it on an oscilloscope in firmware). For numerical Python, the biggest win is usually replacing loops with vectorized NumPy (Lesson 1.2).

## Key takeaways

- Big-O describes growth: $O(1) < O(\log n) < O(n) < O(n\log n) < O(n^2) < O(2^n)$.
- Binary search ($O(\log n)$) needs sorted data; good sorts are $O(n\log n)$; use library routines.
- Pick data structures for the operations you need (hash sets for lookup, ring buffers for queues).
- Measure with a profiler before optimizing.
