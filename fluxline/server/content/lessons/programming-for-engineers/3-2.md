## Never lose work again

**Version control** records every change to a project's files, who made it and why. It lets you undo mistakes, compare versions, work in parallel with a team, and know exactly which code is running on a shipped product. **Git** is the universal standard, for firmware, analysis scripts, FPGA designs, PCB files and documentation alike. (Ohmentum's own lessons are stored in Git.)

## The core workflow

```bash
git clone https://github.com/team/motor-controller.git   # copy a repository
git switch -c fix-overcurrent      # make a branch for your change
# ... edit files ...
git status                         # what changed?
git diff                           # exactly how?
git add src/protection.c           # stage the change
git commit -m "Trip overcurrent within 2 us instead of 10 us"
git push -u origin fix-overcurrent # share it
```

Then open a **pull request** so teammates can review the change before it's merged into the main branch.

Good habits:

- **Small, focused commits** with messages that say what changed and why ("Fix ADC offset by recalibrating at startup"), not "updates."
- **Branch per task**; keep the main branch always working.
- Never commit secrets (passwords, keys) or large generated files (build outputs); list them in `.gitignore`.
- **Tag releases** (`git tag v1.2.0`) so you can rebuild exactly what shipped.

Two especially useful commands: `git log -p file.c` shows a file's history, and `git bisect` binary-searches the history (Lesson 3.1) to find the exact commit that introduced a bug.

## Testing

Untested code is broken code you haven't noticed yet. A **unit test** runs a small piece of code with known inputs and checks the output automatically:

```python
# test_circuits.py  (run with: pytest)
import math
from circuits import parallel, divider

def test_parallel_equal_resistors():
    assert parallel(10e3, 10e3) == 5e3

def test_divider_half():
    assert divider(10.0, 1e3, 1e3) == 5.0

def test_rc_time_constant():
    v = 5 * (1 - math.exp(-1))
    assert math.isclose(v, 3.1606, rel_tol=1e-4)   # compare floats with a tolerance
```

- Test **edge cases**: zero, negative, maximum values, empty inputs, overflow boundaries.
- Compare floating-point results with a **tolerance**, never `==` on computed floats.
- Write a test that reproduces each bug before fixing it, so it can never return.
- Firmware logic (filters, state machines, protocol parsers) can be tested on a PC by keeping it separate from hardware access; hardware-in-the-loop rigs test the rest.

**Continuous integration** (CI) runs the whole test suite automatically on every push and pull request, so a change that breaks something is caught before it's merged.

## Debugging

A systematic approach beats guessing:

1. **Reproduce** the bug reliably, ideally with an automated test.
2. **Isolate** it: shrink the input, comment out parts, bisect the history.
3. **Observe**: use a debugger (breakpoints, stepping, watching variables: `pdb` in Python, GDB or the IDE debugger with a hardware probe for microcontrollers), logging, or a logic analyzer and oscilloscope for timing problems.
4. **Form a hypothesis, test it, fix the cause** (not the symptom), and add a regression test.

Many embedded bugs are timing, memory or hardware interactions: race conditions with interrupts, stack overflows, uninitialized variables, wrong register settings. Reading the datasheet again is a legitimate debugging step.

## Key takeaways

- Git: branch per task, small commits with clear messages, pull requests for review, tags for releases; `git bisect` finds regressions.
- Unit tests check known inputs automatically; test edge cases; compare floats with tolerances; CI runs them on every change.
- Debug systematically: reproduce, isolate, observe, fix the cause, add a regression test.
