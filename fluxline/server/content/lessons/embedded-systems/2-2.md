## Don't keep asking; get told

A program could check a button or a UART in a loop (**polling**), but that wastes the CPU and can miss short events. With **interrupts**, the peripheral signals the CPU when something happens; the CPU suspends what it's doing, runs a short **interrupt service routine** (ISR), and resumes exactly where it left off.

## What happens on an interrupt

On an ARM Cortex-M (RISC-V is similar in spirit):

1. A peripheral raises an interrupt request; the **interrupt controller** (the NVIC on Cortex-M) checks that it's enabled and has higher priority than whatever is running.
2. The hardware **automatically saves** the registers a C function may clobber (r0–r3, r12, lr, pc, xPSR) on the stack.
3. It fetches the ISR's address from the **vector table** (a table of handler addresses at a known location) and jumps there.
4. The ISR runs, typically clears the peripheral's interrupt flag, and returns.
5. The hardware restores the saved registers and the interrupted code continues.

Because the hardware saves the right registers, Cortex-M ISRs are ordinary C functions:

```c
volatile uint32_t ticks;

void SysTick_Handler(void) {   // name matches the vector table entry
    ticks++;                   // keep ISRs short
}
```

**Latency** is the time from the event to the first ISR instruction: 12 clock cycles on a Cortex-M3/M4, so 0.25 µs at 48 MHz, if nothing of equal or higher priority is running.

**Exceptions** use the same mechanism for internal events: faults (illegal memory access, divide by zero), system calls, and the system timer.

## Priorities and nesting

Each interrupt has a **priority**. A higher-priority interrupt can **preempt** a running lower-priority ISR (nesting); equal or lower ones wait until it finishes. Assign the highest priorities to the events with the tightest deadlines (a motor's overcurrent shutdown before a UART receive).

## Rules for writing ISRs

- **Keep them short.** Do the minimum (grab the data, set a flag, push to a buffer), and leave the processing to the main loop or a task. A long ISR delays every lower-priority interrupt.
- **Clear the interrupt flag**, or the ISR re-enters forever.
- **Share data carefully.** Variables shared with the main code must be `volatile`, and multi-step updates must be protected: briefly disable interrupts around the critical section, or use atomic operations. A 32-bit counter read on an 8-bit CPU takes several instructions, and an interrupt in the middle produces a torn, nonsense value.
- **Don't block.** No waiting loops, no `printf`, no `malloc` inside an ISR.

## CPU load

> **Example.** An ADC interrupt fires at 10 kHz, and its ISR (including entry and exit) takes 200 cycles on a 48 MHz CPU. CPU load $= 10^4 \times 200/48\times10^6 = 4.2\%$. At 100 kHz it would be 42%, leaving little for everything else; that's when designers switch to **DMA**, which moves data from the peripheral to memory with no CPU involvement and interrupts only when a whole buffer is full.

## Practice

```quiz
? A Cortex-M4 at 80 MHz has a 12-cycle interrupt latency. What is the latency, in ns?
= 150 | 0.001 | ns
> $12/80\ \text{MHz}$.
```

```quiz
? An ISR takes 400 cycles and fires 5000 times per second on a 16 MHz CPU. What fraction of CPU time does it use, in %?
= 12.5 | 0.001 | %
> $5000 \times 400/16\times10^6 = 0.125$.
```

```quiz
? A UART at 1 Mbaud (10 bits per byte) interrupts once per received byte. How many interrupts per second is that?
= 100000 | 0.001 |
> $10^6/10$; a strong case for DMA.
```

```quiz
? A low-priority ISR is running when a higher-priority interrupt arrives. On a Cortex-M:
+ the higher-priority ISR preempts it, then the lower one resumes
- the higher-priority interrupt is lost
- both run at once
- the lower-priority ISR is aborted and restarted
> Nested interrupts are handled by priority.
```

```quiz
? What is the problem with reading a multi-byte variable that an ISR updates, without protection?
+ An interrupt between the partial reads can produce an inconsistent ("torn") value
- The variable will be stored in flash
- The compiler will refuse to compile it
- The ISR will run twice
> Protect the read with a critical section or use atomic access.
```

## Key takeaways

- Interrupts let peripherals signal the CPU; hardware saves context and jumps through the vector table.
- Priorities decide preemption; latency on Cortex-M is about 12 cycles.
- ISRs must be short, clear their flags, never block, and protect shared data (`volatile` + critical sections).
- High interrupt rates waste CPU time; use DMA for bulk data.
