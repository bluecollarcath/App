## How an instruction gets executed

Every RISC instruction goes through the same five steps:

1. **IF**: fetch the instruction from memory at the program counter.
2. **ID**: decode it and read its source registers.
3. **EX**: compute in the ALU (an add, or an address for a load or store, or a branch comparison).
4. **MEM**: read or write data memory (loads and stores only).
5. **WB**: write the result back to the register file.

The hardware that does this, register file, ALU, memories and the multiplexers between them, is the **datapath**; the logic that steers it for each instruction is the **control unit**.

## Single-cycle vs. pipelined

A **single-cycle** processor does all five steps in one long clock cycle, so the clock period must fit the slowest instruction (a load, which uses every stage).

A **pipelined** processor works like an assembly line: registers between the stages let five different instructions be in five different stages at once. Each instruction still takes five cycles to finish (**latency**), but one instruction **completes every cycle** (**throughput**).

| Cycle | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| instr 1 | IF | ID | EX | MEM | WB | | |
| instr 2 | | IF | ID | EX | MEM | WB | |
| instr 3 | | | IF | ID | EX | MEM | WB |

> **Example.** Stage delays of 200, 100, 150, 200 and 100 ps. Single-cycle: 750 ps per instruction. Pipelined: the clock must fit the slowest stage plus about 20 ps of pipeline-register overhead, so 220 ps. Speed-up $= 750/220 = 3.4\times$, less than the ideal 5× because the stages aren't balanced and the registers cost time.

## Hazards

Instructions in flight depend on each other, and that breaks the ideal one-per-cycle flow.

**Data hazards.** In

```asm
    add t0, t1, t2
    sub t3, t0, t4      # needs t0 before add has written it back
```

the `sub` reads `t0` in ID while the `add` is still in EX. The fix is **forwarding** (bypassing): wires carry the ALU result straight back to the next instruction's ALU input, so no time is lost. One case can't be fully forwarded: a **load followed immediately by a use** of the loaded value, since the data arrives only at the end of MEM. The pipeline must **stall** one cycle (insert a "bubble"), unless the compiler schedules an independent instruction in between.

**Control hazards.** A branch's outcome is known only in EX, but the next instructions have already been fetched. If the branch is taken, they must be flushed: a **branch penalty** of a few cycles. Processors **predict** branches (simple ones assume "not taken"; real ones learn from history and get more than 95% right), so the penalty is paid only on mispredictions.

**Structural hazards.** Two instructions need the same hardware in the same cycle. Separate instruction and data memories (or caches) avoid the most common one.

## Effective CPI

Hazards add stall cycles on top of the ideal CPI of 1:

$$
\text{CPI} = 1 + \sum(\text{frequency} \times \text{penalty})
$$

> **Example.** 20% of instructions are loads, and half of them are followed immediately by a use (1-cycle stall): $+0.1$. 15% are branches, mispredicted 10% of the time with a 3-cycle penalty: $+0.045$. CPI $= 1.145$.

High-performance cores go further: deeper pipelines (higher clock, bigger branch penalties), **superscalar** issue (several instructions per cycle, CPI below 1) and **out-of-order** execution. Microcontrollers such as the Cortex-M0 use short 2–3 stage pipelines: simple, low-power and predictable, which matters for real-time code.

## Key takeaways

- Five stages: IF, ID, EX, MEM, WB. Pipelining overlaps them for about one instruction per cycle.
- The clock fits the slowest stage plus register overhead; unbalanced stages limit speed-up.
- Data hazards: forwarding, plus a 1-cycle load-use stall. Control hazards: branch prediction.
- CPI $= 1 + \sum$ frequency × penalty.
