## Fast memory is small; big memory is slow

A processor can execute an instruction in under a nanosecond, but main memory (DRAM) takes 50–100 ns to respond. If every load went to DRAM, the processor would spend 99% of its time waiting. The solution is a **memory hierarchy**: small, fast memories close to the processor, backed by larger, slower ones.

| Level | Typical size | Access time |
|---|---|---|
| Registers | ~100 bytes | < 1 cycle |
| L1 cache (SRAM) | 32–64 KB | 1–4 cycles |
| L2/L3 cache (SRAM) | 256 KB – 32 MB | 10–40 cycles |
| Main memory (DRAM) | GB | 100–300 cycles |
| Flash / SSD | GB – TB | 10–100 µs |

Microcontrollers have a flatter hierarchy: on-chip SRAM is fast enough to need no cache, but code runs from flash memory, which is slower than the CPU above a few tens of MHz, so faster MCUs add a small flash cache or prefetch buffer.

## Why caches work: locality

Programs don't access memory randomly:

- **Temporal locality:** recently used data is likely to be used again soon (loop variables, the instructions of a loop).
- **Spatial locality:** data near recently used data is likely to be used soon (the next array element, the next instruction).

A cache keeps recently used **blocks** (lines, typically 32–64 bytes) so that most accesses **hit** and only a few **miss** and go to the slower level.

## Average memory access time

$$
\text{AMAT} = t_{hit} + (\text{miss rate}) \times (\text{miss penalty})
$$

> **Example.** L1 hits in 1 cycle with a 5% miss rate, and a miss costs 100 cycles to DRAM: $\text{AMAT} = 1 + 0.05 \times 100 = 6$ cycles. Six times slower than a perfect cache, and a 2% miss rate would make it 3. Small changes in miss rate matter enormously.
>
> **Adding an L2** (10 cycles, 20% local miss rate): L1's miss penalty becomes $10 + 0.2 \times 100 = 30$ cycles, so $\text{AMAT} = 1 + 0.05 \times 30 = 2.5$ cycles.

## Cache organization

An address is split into three fields:

$$
\underbrace{\text{tag}}_{\text{which block?}}\ \big|\ \underbrace{\text{index}}_{\text{which set?}}\ \big|\ \underbrace{\text{offset}}_{\text{which byte in the block?}}
$$

- **Direct-mapped:** each block can go in exactly one place (one way per set). Simple and fast, but two hot blocks that map to the same set keep evicting each other (**conflict misses**).
- **N-way set-associative:** each set holds $N$ blocks, so up to $N$ blocks with the same index can coexist. 4- to 8-way is typical for L1.
- **Fully associative:** a block can go anywhere. No conflicts, but expensive to search.

> **Example.** A 32 KB, 4-way cache with 64-byte blocks and 32-bit addresses: $32768/64 = 512$ blocks, $512/4 = 128$ sets. Offset: 6 bits ($2^6 = 64$), index: 7 bits ($2^7 = 128$), tag: $32 - 6 - 7 = 19$ bits.

## Writing code that the cache likes

Traversing a 2-D array in C along rows (consecutive addresses) uses every byte of each fetched block; traversing down columns can miss on every access and run ten times slower, with identical arithmetic. Keeping hot data together, using smaller data types, and processing data in cache-sized tiles are some of the most effective optimizations there are.

**Embedded caution:** caches make timing **unpredictable** (a hit and a miss differ by 100×), which is a problem for hard real-time code. Real-time systems use **tightly coupled memories** (TCM), cache locking, or no cache at all for critical routines. And when a peripheral's DMA writes to memory behind the CPU's back, the cache may hold stale data unless it's invalidated: a classic embedded bug.

## Key takeaways

- A hierarchy of small fast memories in front of large slow ones works because of temporal and spatial locality.
- $\text{AMAT} = t_{hit} + \text{miss rate} \times \text{penalty}$; multilevel caches shrink the penalty.
- Addresses split into tag, index and offset; associativity reduces conflict misses.
- Caches make timing variable; real-time code uses TCM or cache locking, and DMA needs cache maintenance.
