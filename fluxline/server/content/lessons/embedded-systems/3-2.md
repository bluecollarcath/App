## Beyond the super-loop

Small firmware is often a **super-loop**: `while (1) { read_sensors(); update_control(); refresh_display(); }`, with interrupts for urgent events. It's simple and predictable, until the jobs have very different timing needs. If the display refresh takes 30 ms, the control loop can't run every 1 ms. A **real-time operating system** (RTOS) such as FreeRTOS, Zephyr or ThreadX solves this by running independent **tasks** and letting a **scheduler** decide which runs when.

"Real-time" doesn't mean fast. It means **deadlines are guaranteed**: an airbag controller that always responds within 10 ms is real-time; a faster PC that usually responds in 1 ms but sometimes takes 200 ms is not.

## Tasks and preemptive scheduling

Each task is a function with its own stack, written as if it had the CPU to itself:

```c
void control_task(void *arg) {
    for (;;) {
        read_encoder();
        update_pid();
        vTaskDelay(pdMS_TO_TICKS(1));   // block for 1 ms, letting other tasks run
    }
}
```

A task is **running**, **ready** (waiting for the CPU) or **blocked** (waiting for time, data or an event). The usual RTOS scheduler is **preemptive and priority-based**: the highest-priority ready task always runs, and if a higher-priority task becomes ready (its delay expires, or an interrupt hands it data), it **preempts** the current one immediately. Switching saves one task's registers and restores another's: a **context switch**, a few microseconds on a microcontroller.

## Rate-monotonic scheduling

For periodic tasks with execution time $C_i$ and period $T_i$, giving higher priority to **shorter periods** (rate-monotonic scheduling) is optimal among fixed-priority schemes. Liu and Layland proved that all deadlines are met if the total CPU utilization satisfies

$$
U = \sum_{i=1}^n\frac{C_i}{T_i} \le n\left(2^{1/n} - 1\right)
$$

The bound is 0.828 for 2 tasks, 0.780 for 3, and approaches $\ln2 = 0.693$ for many. (It's sufficient, not necessary: sets above it may still be schedulable on closer analysis.)

> **Example.** Tasks with $(C, T)$ = (1, 4), (2, 10) and (3, 20) ms: $U = 0.25 + 0.2 + 0.15 = 0.60 \le 0.78$, so rate-monotonic priorities guarantee every deadline.

## Sharing safely: semaphores, mutexes and queues

Tasks preempt each other at any instruction, so shared data needs protection, just as with ISRs (Lesson 2.2):

- A **mutex** guards a shared resource (an SPI bus, a data structure): a task takes it before access and gives it back afterward; others block until it's free.
- A **semaphore** signals events or counts resources. A common pattern: an ISR gives a semaphore, and a task waiting on it wakes to do the heavy processing.
- A **queue** passes data between tasks (or from an ISR to a task) safely, with built-in blocking.

## Priority inversion

A classic trap: a low-priority task holds a mutex that a high-priority task needs, and a **medium**-priority task preempts the low one, so the high-priority task waits for the medium one, indefinitely. That's what repeatedly reset the Mars Pathfinder lander in 1997. The fix, **priority inheritance** (the mutex holder temporarily inherits the waiting task's priority), was enabled by a patch uploaded to Mars. RTOS mutexes provide it; plain semaphores don't, so use mutexes for mutual exclusion.

Other hazards: **deadlock** (two tasks each holding a mutex the other needs; prevent by always taking locks in the same order), stack overflow (each task has its own stack; size it and check its high-water mark), and starvation of low-priority tasks.

## Key takeaways

- An RTOS runs independent tasks under a preemptive, priority-based scheduler.
- Rate-monotonic: shorter period = higher priority; schedulable if $U \le n(2^{1/n} - 1)$.
- Use mutexes (with priority inheritance) for shared resources, semaphores for signaling, queues for data.
- Watch for priority inversion, deadlock and per-task stack overflow.
