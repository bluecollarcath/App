## Pins you control from software

**General-purpose I/O** (GPIO) pins are the simplest peripheral: each can be configured as a digital output (driving high or low) or an input (reading a level). They drive LEDs, relays and chip-select lines, and read buttons, switches and status signals.

## Memory-mapped I/O

On a microcontroller, peripherals are controlled through **registers** that appear at fixed memory addresses. Writing to a GPIO's output register is literally a store instruction to a special address:

```c
#define GPIOA_MODER (*(volatile uint32_t *)0x48000000)  // mode: 2 bits per pin
#define GPIOA_ODR   (*(volatile uint32_t *)0x48000014)  // output data
#define GPIOA_IDR   (*(volatile uint32_t *)0x48000010)  // input data

GPIOA_MODER = (GPIOA_MODER & ~(3u << 10)) | (1u << 10);  // pin 5 = output
GPIOA_ODR  |=  (1u << 5);                                // drive pin 5 high
if (GPIOA_IDR & (1u << 0)) { /* pin 0 reads high */ }
```

(Addresses are from an STM32; every family has its own, published in its reference manual, and vendor headers wrap them in named structures.)

Two essentials:

- **`volatile`** tells the compiler that the location can change, or has effects, outside the program's control. Without it, the optimizer may cache a register's value or delete "redundant" writes, and the code silently stops working at higher optimization levels.
- **Bit manipulation:** set a bit with `|= (1u << n)`, clear it with `&= ~(1u << n)`, toggle with `^=`, test with `&`. Fields wider than one bit are cleared with a mask, then set.

**Read-modify-write races.** `ODR |= mask` is three steps (load, OR, store). If an interrupt changes another bit of the same register in between, its change is lost. Many MCUs provide **bit set/reset registers** (writing a 1 sets or clears just that pin, atomically) to avoid this.

## Electrical details

**Outputs** can be **push-pull** (actively driven both high and low) or **open-drain** (pulled low or released; an external resistor pulls high, which allows several devices to share a line, as on I²C). Each pin can source or sink only a limited current, typically a few to 20 mA.

> **LED resistor.** A red LED (2.0 V forward drop) on a 3.3 V pin at 10 mA needs $R = (3.3 - 2.0)/0.01 = 130\ \Omega$.

**Inputs** must never float: an unconnected CMOS input picks up noise and can draw extra current. Enable an internal **pull-up** or **pull-down** resistor (typically 20–50 kΩ), or add an external one. A button wired from the pin to ground with a pull-up reads 1 when released and 0 when pressed. While the button is pressed, the pull-up draws $3.3\ \text{V}/40\ \text{k}\Omega = 83\ \mu$A, which matters in battery devices.

## Debouncing

Mechanical contacts **bounce**: when a button closes, it makes and breaks contact many times over 1–10 ms. Read naively, one press counts as a dozen. Fixes:

- **Hardware:** an RC filter plus a Schmitt-trigger input.
- **Software:** sample the pin periodically (every 5 ms, say) and accept a new state only after it has been stable for several consecutive samples.

```c
// Called every 5 ms from a timer: accept a change after 4 identical reads (20 ms).
static uint8_t count; static bool stable;
bool raw = !(GPIOA_IDR & 1u);           // active-low button
if (raw != stable) { if (++count >= 4) { stable = raw; count = 0; } }
else count = 0;
```

## Key takeaways

- Peripherals are controlled through memory-mapped registers; access them via `volatile` pointers.
- Set, clear and test bits with masks; beware read-modify-write races (use set/reset registers).
- Outputs: push-pull or open-drain, current-limited. Inputs: never floating; use pull-ups/downs.
- Debounce mechanical inputs in hardware or by requiring stable consecutive samples.
